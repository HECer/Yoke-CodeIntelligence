# Managed generic host installation

The `host_install` module is being developed and tested against owned temporary fixtures. It does not install into the developer's real agent, home or Git configuration during development. The initial profile is `generic-agents-v1`, which manages one instruction block in explicitly selected `AGENTS.md` files. This does not certify installation into any branded client's configuration or implement prompt/edit/session hooks.

The host explicitly selects an installation label, existing absolute target directories, a native executable, a host policy file and an existing private state directory outside the targets. Planning and status must not open a source Engine or Store, create state files or change configuration. Executable and policy bytes are hashed without executing the executable or persisting policy contents.

`plan_install` and `plan_uninstall` return strict, deterministic plans for a supplied timestamp. Plans bind the profile/schema, physical root identities, executable/policy identities and hashes, exact target before/after hashes, receipt revision, owned byte edits and expiry. An absent target differs from an existing empty file. A serialized plan never creates write authority: the host separately constructs `WriteAuthority` only after its explicit write gate.

Installation receipts establish ownership. A matching marker in a file is not sufficient. Human content outside an unchanged owned block is preserved, including UTF-8 BOMs and line endings. Unknown, duplicated, nested or altered managed blocks require reconciliation. Uninstall removes only the receipt-owned fragment. An installer-created file is removed only when removing the managed fragment leaves it empty; an originally existing empty file remains present.

All targets, authority bindings, ownership proofs and capacity limits are admitted before the first target write. Windows publication uses held file handles denying foreign write/delete access, same-handle no-replace moves, and same-directory original backups. The original retains its file identity and ACL while recovery is pending. Output publication never replaces a foreign file that appears in the temporary path gap. That conflict requires recovery and preserves both the original backup and foreign file.

Production namespace operations walk, open, create, query and enumerate entries relative to held directory handles. Name lookup refuses reparse traversal; changing metadata on a held directory must never redirect an operation into the reparse target. Sharing flags do not prevent every metadata change. Handle-derived Volume GUID paths are internal persisted bindings and authorize operations only through an exact match to the current host selection; raw user GUID, device and UNC paths remain refused. Deadlines are cooperative checks between bounded synchronous local OS calls and cannot forcibly cancel a blocked kernel call.

The private host state keeps plans, receipts, hashes, owned fragments and per-file transition metadata. It does not keep full unrelated instruction/configuration files or policy content. Final temporary output and a temporarily renamed original necessarily exist in the target directory with appropriate protections while a change commits; those bytes are never copied into analyzed source state or a private journal. Backup cleanup must verify ownership and identity.

Recovery has explicit resume and rollback modes. It changes only files matching the journal's exact identities/content states. Foreign writes remain untouched. Multi-file changes are not atomically visible, and a failed or interrupted transition remains `recovery_required` until verified recovery completes. There is no recursive directory deletion, automatic upstream plugin removal, home-directory discovery, client/model invocation or background indexing.

The immutable installation receipt is the ownership commit point. Before that point, rollback restores the original objects and records its result in the journal without advancing the installation's ownership history. A durable `rolling_back` event prevents changing that transaction back to Resume. After receipt publication, Resume may finish cleanup; removing the installation requires a separately reviewed uninstall plan. Retrying a completed plan or journal verifies the current ownership head, actual target identities and hashes, auxiliary paths and completed cleanup before returning its receipt.

Planning uses `host-install plan --selection host.json` or `host-install uninstall-plan --selection host.json`. The strict selection contains `installation`, `targetRoots`, `executable`, `policy` and `stateRoot`; all paths are explicit and absolute. Applying requires `host-install apply --selection host.json --plan plan.json --allow-host-writes`. Journal recovery uses `host-install recover --selection host.json --journal ID --mode resume|rollback --allow-host-writes`. The write gate precedes loading host-controlled inputs or opening writable host state. Neither planning nor status creates a source Engine, source Store or host state.

An interrupted initialization that has not published `schema.json` has no transaction journal. `host-install recover-initialization --selection host.json --plan plan.json --allow-host-writes` is a separate repair operation. It validates the original initial-install plan, its expiry, physical bindings and a token derived from that exact plan. It accepts only the known empty scaffold, plus an exact matching schema or initialization receipt. Unknown entries, nonempty transaction directories, linked locks and changed preconditions are preserved and rejected. The typed `initialization.json` receipt is written before schema activation and supports the same-plan retry. Planning and status never perform this repair.

Inputs are bounded to 16 target roots, 1 MiB per instruction or policy file, and an 8 MB encoded plan/protocol row. The executable is hashed through a guarded stream without retaining its contents; executable hardlinks are permitted only for that immutable binding. Targets, policy and state files require a single link. Private metadata limits are 1,000 rows per plans/receipts directory, 1,000 journal directories and 256 events per journal; the 32 MB byte limit applies separately to each bounded metadata directory, not to the whole state tree or process. Admission includes preserved temporary entries and prospective receipt/event bytes. No automatic history deletion is implemented.

Windows prepared outputs must preserve the original owner, group, DACL entries, inheritance/control semantics and mandatory label before receiving any human bytes. Unsupported security states fail closed. The original backup retains its object identity and security metadata. Full audit SACLs, arbitrary file attributes and operating-system power-loss durability are outside the current claim.

Owner/group/DACL reads use the bounded, self-relative descriptor returned by [`GetKernelObjectSecurity`](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-getkernelobjectsecurity) through the already held file handle. Owned Windows fixtures exposed `GetSecurityInfo` reporting legacy explicit ACEs as inherited even while the stored ACE flags remained explicit; copying that representation changed the output's inheritance metadata. Independent path-based readback now checks an explicit legacy child ACL under an inheritable parent for both empty armed and populated prepared outputs. No ACE flags are masked or normalized during comparison. A pending historical journal whose security hash was derived from the converted representation can fail its exact baseline check; recovery preserves and refuses that state rather than rewriting its journal or accepting an alternative fingerprint.

New transactions use strict private journal schema 2; public plans and receipts remain schema 1. At the start of guarded apply, every existing original receives a supported-security fingerprint before the initial journal event. That fingerprint is required exactly when an original exists and remains immutable throughout the event chain, including allocation retries and rollback. The journal stores hashes rather than security descriptors. Each output attempt separately binds its exact native file identity and security fingerprint. Reads validate every immutable event and the complete sequence, predecessor links, transitions and receipt evidence. Unknown journal schemas fail closed; schema 1 recovery remains separate.

Output preparation has an explicit ownership handoff. An `allocating` event precedes creation of an empty auxiliary file with deletion on close. The installer durably registers its exact identity and security fingerprint before clearing deletion on close through that same held handle. A durable `populating` event precedes the first human byte. Appends admit only the remaining bytes of the canonical output, in bounded chunks; an interrupted raw prefix may end inside a UTF-8 code point. Exact bytes remain authoritative. Full output hashing and flushing precede a durable `prepared` event, which is mandatory before publication can begin.

Process death before registration leaves no human bytes in the allocated file. Windows removes the empty object when the relevant handle cleanup completes. Recovery requires a strict missing-file result before starting another attempt; access denial, delete-pending state, a retained reader or a foreign occupant cannot be treated as absence. A registered empty object may also disappear if the process dies before disarming deletion on close. Only these admitted early states permit a new allocation, with at most three durable attempts per target and immutable abandoned-attempt history. Reaching that cap does not prevent Rollback. A missing `populating` output cannot restart Resume, and a foreign replacement is never adopted because its bytes or path resemble the expected output.

Both precommit recovery modes check all original roles and supported-security baselines before changing any journal or target. Prepared outputs must match the latest active attempt's exact identity and security fingerprint, including outputs already moved to `AGENTS.md`. Preparation and precommit publication or rollback repeat the applicable checks before appends, finalization, moves, rollback deletion and receipt commit. These checks detect stale security at those boundaries; file sharing flags do not atomically prevent later DACL or label changes. After the receipt commit point, cleanup leaves the installed target's subsequently changed ACL untouched. A completed `rolled_back` replay conservatively still requires the original historical security fingerprint: later legitimate ACL changes can cause a read-only refusal without changing files or history.

The Windows test suite includes actual child processes driving `apply()`, followed by process exit or forced termination at allocation, registration, disarming, population, partial append, flush and prepared boundaries. It also checks live original/output ACL changes, retained readers, hostile replacements, immutable security baselines, retry exhaustion and raw prefixes. Separate tests still construct durable interruption layouts; those are not process-kill evidence. The disposition primitive was exercised on local NTFS under Windows 10.0.26300. Unsupported runtime disposition/security operations fail closed. These results do not establish power-loss durability, support for every filesystem, or atomic visibility across multiple targets.

A focused debug test completed a 16-target recovery in 24.020 seconds with its unchanged 30-second cooperative deadline. Diagnostic inclusive spans included 23.518 seconds across 51 journal appends, 13.933 seconds across 52 full history loads, and 8.096 seconds across 54 capacity scans. These spans overlap and must not be summed. This is local test evidence, not a release benchmark or latency guarantee. Reusing a held metadata-directory reader within each scan remains a separate future optimization; no history or content checks are skipped to obtain this result.

Legacy schema 1 can still leave an unidentified auxiliary file if a process dies before journaling its identity. That recovery path preserves and refuses the file and requires explicit reconciliation. Schema 2 likewise preserves and refuses any unknown auxiliary occupant. Hash or path resemblance never establishes ownership. Private host state is an explicitly host-controlled authority boundary; record hashes establish consistency and do not authenticate storage writable by an adversary.
