# Parent-managed embedding batches

`provider_batches` adds explicit host-selected batching for native Bedrock embedding workers. Existing `ProviderSpec`, single-request operations, protocol schema 1, request-ID tuples, vector collection IDs, and legacy receipts are unchanged. No batch is selected by default.

Create a non-deserializable `EmbeddingBatchPolicy::for_bedrock(spec, max_calls, max_entities, max_total_source_bytes)` in trusted host code. Limits are 1–256 attempts, 1–2000 entities, and 1–10,000,000 selected UTF-8 bytes. Titan uses one entity per child request; Cohere uses at most 96. V3 uses a conservative 512-byte source excerpt; other dialects use at most 5000 bytes. Excerpts preserve exact source anchors and omitted-byte counts. These local admission limits are not tokenizer or service-acceptance claims. There is no implicit entity truncation, automatic retry, or automatic resume.

`generate_embeddings_batched` requires the workspace's exclusive client lease for the complete operation. Other open state clients cause denial before spending. Each managed child is a stdio-only worker and must not open that same workspace. The lease prevents other normal clients from consuming sink capacity or changing ledger/record preconditions during generation. No SQLite transaction is held over a model request.

Before any reservation or child launch, the parent validates the immutable graph and captured source proofs, every sink anchor, exact expected dimensions, all selected entity IDs, source and serialized-request budgets, chunk count, complete worst-case monetary reservation, and worst-case normalized vector JSON/storage capacity. An existing immutable `(snapshot, model@version)` vector namespace is refused before spending; choose a new explicit model version. Ordinary source read permission remains separate from write authority, including explicitly captured read-only dependencies.

All attempts and the initial strict `native_model_batch_v1` record are created in one SQLite transaction. Each private single-use reservation is consumed by a guarded send transition. A reported cost overrun blocks subsequent sends even though their reservations already exist. Every chunk uses the original native protocol and exactly one owned worker invocation. The native Bedrock worker makes one HTTP attempt and does not fan out behind that reservation.

Complete bound failed responses retain valid reported cost and usage before their output is rejected. Safe per-chunk response artifacts retain identities, source bindings, original response usage/cost, and validated vectors only for successful output. Partial vectors are never published as a corpus. After every chunk succeeds, the exact normalized legacy collection and completed batch record commit in one SQLite transaction. Any publication failure rolls both back while preserving prior attempt accounting and response artifacts.

On failure, the parent cancels only attempts that remain durably `Reserved`. A dispatched, timed-out, or uncertain attempt retains its reservation and unknown billing unless a valid report settles it. Cancellation or deadline expiration may prevent releasing still-unsent reservations; inspection reports those IDs honestly. Use a later explicitly authorized ledger cleanup request if needed. An interrupted operation remains inspectable and does not restart workers.

`describe_embedding_batch(store, batch_id, deadline)` performs bounded reads and validates source replay, original native request IDs, current ledger links, exact response artifacts, and completed collection bytes. It never executes a worker. Original unknown cost or usage may subsequently become known through ledger reconciliation; a later usage event does not rewrite the original response receipt. Originally known usage remains bound to its immutable `response` event rather than the ledger's maxima across other event names. Aggregate cost/usage are known only when every attempt supplies a report. Per-attempt records remain authoritative for partial and unknown accounting. Valid usage sums exceeding numeric JSON's u64 range remain exact in `knownReportedUsageDecimal`, with `reportedUsageOverflow: true` and null numeric aggregates. Overflow does not increment the missing-report count or invalidate a completed corpus. A failed batch reports an unknown remote model-call count alongside dispatched attempts, confirmed responses, uncertain IDs, and unreleased unsent IDs.

Typed retention must replay the batch/source/ledger/response/vector bindings and retain validated response CAS references. Adding the record kind to an opaque allowlist is insufficient. These records document local source binding and provider-reported claims; they do not attest model quality, actual AWS prices, or externally verified billing.

No real AWS calls, real credentials, or paid inference are used by the default tests. The labeled child-process fixtures exercise native request/accounting behavior. Separate ignored Windows CLI fixtures use unique fake OS credentials and owned loopback HTTP connections, then remove only their created credential generations.
