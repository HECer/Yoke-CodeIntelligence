# Host-selected Docker verification

`container::execute_container` runs a prepared immutable change snapshot only after explicit host `--trust-project` and an isolation choice. The executable, executable prefix arguments, local daemon endpoint, image and command argv are host inputs. Every invocation pins `--host` to the selected local Unix socket or Windows named pipe. Remote endpoints and conflicting host/context prefix arguments are refused; Docker's default context cannot select another daemon. A repository or MCP request cannot select these inputs or authorize execution. The image must be a locally installed `name@sha256:<64 lowercase hex>` digest; image tags, automatic pulls and network fallback are refused.

The Linux container receives no network, drops all capabilities, enables `no-new-privileges`, uses a numeric nonroot user and a read-only root filesystem. The immutable copied snapshot is bound read-only at `/source`. Bounded `/work` and `/tmp` tmpfs mounts provide temporary build space; the working directory is `/work`. The host command may copy source into temporary build space explicitly. Memory, CPU and PID limits are mandatory and bounded. No host PID/network namespace, privileged mode, daemon/socket mount or writable source mount is offered.

The CLI process uses the shared bounded process runner and request deadline. Docker creates an exact container ID in an owned private cidfile. Cleanup uses only that validated full ID, with a separate finite deadline for stop/remove and confirmation that the exact ID is absent. A timeout, unknown container ownership or unconfirmed cleanup produces a failed verification. A copied snapshot is checked in full after execution, including unexpected files and links. Source integrity or cleanup failure cannot authorize workspace application.

Verification stores the existing `verification` receipt with `level:"executed"`; syntax-only receipts remain separate. A successful process exit is insufficient. A host-selected test-output pattern must contain one numeric capture and report a positive executed-test count. Unknown or zero test counts fail. This count is a trusted test runner's output assertion, not independent proof of exhaustive coverage or resistance to a deliberately dishonest approved test command.

The standard Windows tests include clearly labeled Docker CLI process fixtures that exercise policy, receipts, exact cleanup, source mutation, unexpected files, deadline cancellation and zero-test failures. They do not establish daemon containment. The ignored live test requires `YOKE_DOCKER_TEST_IMAGE` to name a preinstalled digest-pinned Linux image with BusyBox-compatible tools and an actual local Docker daemon; absence is failure. It verifies captured source bytes, numeric user, source mount flags, capabilities, `no-new-privileges`, network routes, cgroup memory/PID limits and writable build scratch. The Docker daemon, image and host-selected executable remain trusted dependencies. Live validation on one local daemon does not establish cross-platform daemon certification.

On 2026-10-14, the actual Windows Docker Desktop Linux daemon gate passed with the preinstalled `busybox@sha256:9db7b59979c38555a39def84a31fb98b5296952f9e3afd4f6f11f05b07adfab0` image. Thirteen source/isolation assertions passed, including the attempted read-only source write and CPU quota. A separate actual command exit 7 produced a failed verification receipt. Both exact owned containers were removed and their absence confirmed. No image was pulled. Native Linux/macOS host execution and other daemon/image combinations remain unexecuted here.
