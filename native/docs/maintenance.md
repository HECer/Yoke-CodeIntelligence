# Conservative native maintenance

`maintenance::collect(&Store, &Policy, &Deadline)` is an explicit host operation. It is not exposed through MCP or the editor HTTP API. `Policy::default()` is a dry run with a 24-hour minimum blob age. Set `apply` only after reviewing the report. `minimum_age_ms` ranges from zero through 365 days; future filesystem timestamps are deferred.

This first native pass **retains every snapshot, graph, parse cache entry and generic record**. It does not guess that an old plan, completed journal, expired session, unknown record type or vector/media artifact has become disposable. Native snapshots lack the typed chronology and lifecycle ownership needed for reliable history retirement. Consequently `retiredSnapshots` and `reclaimedBytes` are zero, and the report explicitly marks snapshot retirement and irreversible removal unsupported. `purge_quarantine: true` fails rather than silently claiming a purge.

`pin` validates an existing snapshot and saves a named `snapshot-pin` record; `unpin` removes that explicit pin. Unpinning does not remove its snapshot under the conservative policy.

Reachability includes 64-character lowercase hexadecimal IDs in persisted JSON values, object keys, and snapshot/graph/cache/record primary keys. This protects current/history source bytes, named pins, prepared changes, recovery journals, receipts, editor buffers, knowledge/vector records, media records and future record kinds using the same hash contract. All record ages and status fields are ignored as deletion authority. Arbitrarily encoded external references and independent copies of an unrooted artifact ID are not a proven local root; there is no cross-host reference oracle.

Malformed JSON, malformed native snapshot/graph/extraction shapes, unknown database tables and corrupt quarantine manifests refuse collection before sweeping. Errors avoid printing arbitrary nested JSON. Snapshot source hashes must have valid content-ID shape. Unmanaged blob-directory entries are retained and counted, never recursively removed.

Both dry runs and apply use the Store's exclusive client operation. Every native Store holds a shared `clients.lock` for its lifetime; an admission gate prevents a new client from racing lock upgrades/restoration. Maintenance refuses while another native client is open. It does not close or kill that client. A process crash releases OS locks. Raw SQL/file writers that ignore this protocol are outside the supported cooperation boundary.

The report distinguishes all unreferenced blobs, age-eligible unreferenced candidates, younger/future-dated deferrals, protected blobs, unsupported entries and eligible bytes. Dry runs do not create a quarantine directory or move source bytes. Counts describe the observed state; a pending recovery run is reported separately, and apply restores it before computing its new candidate list.

Apply moves age-eligible orphan blobs into `.yoke/quarantine/RUN_ID/HASH`. It validates the state/blob/quarantine directories and every controlled leaf against links and Windows reparse points. Paths come from fixed local directories and validated hashes. Candidate contents are SHA-256 checked before each move. Source files, snapshots, graph history and protected blobs remain present.

A synchronized, strict `manifest.json` contains the full planned hash list before any rename. An immediate SQLite transaction records the final `maintenance-committed` marker only after all moves finish. No blob is irreversibly removed. `quarantinedBytes` describes bytes moved; it does **not** represent freed disk space.

If hashing, a move, SQLite work or a pre-commit deadline check fails, metadata rolls back and earlier moves receive at most one additional second of cleanup. Every cleanup hash chunk and rename checks that separate budget. Cleanup does not overwrite a foreign destination with a different hash. If cleanup cannot complete, orphan bytes remain safely quarantined, the prepared manifest remains, and the operation fails with the exact recovery run ID. A later apply restores incomplete runs before marking. Failed transaction admission performs no unnecessary marker deletion or second busy wait. Successful SQLite COMMIT is the completion point; the operation does not undo a completed quarantine because a clock check immediately afterward would have expired. A committed quarantined blob that later becomes reachable through local metadata is restored as well. Equal existing bytes are preserved as a duplicate rather than irreversibly deleted.

The manifest file and SQLite commit marker are synchronized; rename/directory durability across sudden power loss is filesystem/platform-dependent. This is a crash-recovery workflow, not a claim of an OS-atomic multi-file filesystem transaction. A malformed or externally altered manifest is retained for inspection rather than treated as empty complete recovery.

Capacity limits are 200,000 rows per metadata table, 128 MB of serialized metadata per row, 200,000 blob entries/candidates, 10,000 quarantine runs, 16 MiB per quarantine manifest and two million JSON nodes per reachability walk. Exceeding a limit fails closed. The shared deadline is checked during scanning, hash streaming, moves and database work.

`native/tests/maintenance.rs` exercises real stores and files: dry-run counts and age deferral, all generic/history roots, pins, foreign-client lock contention, raw SQLite writer contention with bounded failed cleanup and preserved recovery identity, malformed records/snapshot shapes, interrupted-run restoration, SHA-256 failure after an earlier move, metadata rollback, expired deadlines, purge refusal, primary-key/dictionary-key roots and actual link refusal. A module test verifies an expired rollback budget preserves quarantined bytes and a later apply recovers them. This is conservative orphan quarantine, not full TypeScript retention parity or a general physical-disk garbage collector.
