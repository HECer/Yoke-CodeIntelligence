# Explicit history retirement and quarantine purge

These are host-only library and CLI operations. Source text, repository configuration and MCP arguments cannot grant state deletion permission. Ordinary `maintenance::collect` continues to preserve every snapshot and record.

`retention::plan` returns a reviewable, expiring `planId` derived from the exact plan bytes, including a hash of all reviewed snapshot, graph and search rows. It retains the current snapshot, pins, editor/workflow dependencies, foreign-source receipts, knowledge, vectors, media, artifacts and all cache records. Hash-validated JSON artifact payloads retain nested source bindings; opaque payloads, unknown record kinds and unknown nested metadata shapes block reclamation. Corrupt metadata and unknown database tables fail before mutation. Retained snapshot and graph references are followed conservatively. New publications record their actual first publication time atomically. Existing history receives no invented age receipt; a positive minimum history age defers snapshots whose age cannot be proved. The explicit zero minimum requests no history age condition.

`retention::apply(store, plan_id, confirmed_hash, allow_state_deletion, deadline)` requires both an exact plan confirmation and a separate host state deletion permission. It acquires the exclusive client lease and SQLite writer transaction, rechecks the state fingerprint and removes only the listed unrooted snapshot/graph/search rows. A durable manifest retains the retired metadata and search rows; the committed receipt is atomic with the deletions. Original source and source blobs are unchanged. Logical SQLite deletion is reported separately from physical bytes: retirement reports zero reclaimed bytes.

`retention::recover` validates uncommitted history manifests and restores only missing or identical rows. Conflicting foreign rows or unavailable/corrupt source bytes require recovery instead of an overwrite. Committed retirement is replayable through its retained receipt and is not automatically undone.

After retirement, existing maintenance can quarantine CAS blobs that have become demonstrably unreferenced. Quarantine still preserves physical bytes. `retention::purge_plan` reviews only blobs in earlier committed maintenance runs, after the host-selected minimum quarantine age. `retention::purge` requires a separate exact confirmation and state deletion permission, rechecks age and all live roots, validates each hash and path, and rejects links/reparse points, multiple hard links or undeclared entries. It never purges active CAS, unknown state, source files, manifests or receipts. Retired metadata and search text remain in the audit manifest and durable receipt; purging CAS does not erase these audit copies or constitute secure erasure.

Purge records durable intent before irreversible removal. Pending intent explicitly roots all candidate blob IDs for other maintenance and purge plans. Per-file progress and actual removed file-byte counts survive partial failures. `reclaimedBytes` counts the content sizes of files successfully removed, rather than a measured filesystem free-space or net-allocation change. A crash after removal but before the progress receipt records completion is reported separately as `unverifiedRemovalBytes`. A partial purge is reported with `complete:false`, and must not be described as successful complete destruction. A failed or expired operation does not create implicit permission to retry a changed plan. Keep a backup before authorizing irreversible removal of valuable state.

The client lease protects cooperating native clients; it is not isolation from a hostile host process. Same-account filesystem replacement remains outside the security boundary. Tests use temporary fixture workspaces only.
